# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

CEDIM Web is the official site for the Centro de Desarrollo e Investigación en Mecatrónica (CEDIM) at Universidad Nacional de Ingeniería (UNI). It is a **static site**: plain HTML5, CSS3, and vanilla JavaScript — no framework, no bundler, no package manager, no build step, no test suite.

## Running the site

There is no build/lint/test tooling in this repo, and none is wanted — GitHub Actions was considered and declined, since a site with no build step gains nothing from it. To view changes, open any `.html` at the root directly in a browser or serve the directory statically. Deployment is a plain `git push`: merge `develop` into `main`, push, and GitHub Pages publishes in about a minute.

## Architecture

**The site is multi-page, and every page lives at the repo root.** `index.html`, `about.html`, `research.html`, `projects.html`, `open-calls.html`, `workshops.html`, `project.html` (project detail), and `404.html`. Flat on purpose: every asset reference is then the same string from every page, which removes the whole class of `../` bugs that appeared when the detail page briefly lived under a `pages/` subfolder (since deleted). Put a new page at the root and add it to `NAV_ITEMS`.

**The site is English-only, deliberately.** All user-facing text, page filenames, and project `id` slugs are in English because CEDIM wants international reach; pages declare `lang="en"`. Code comments and the editing instructions inside `assets/js/data/projects.js` stay in Spanish, since those serve the CEDIM team rather than the public. Keep new content on the same split.

**Navbar and footer are injected by JS from one place.** Each page declares only `<div id="site-navbar"></div>` and `<div id="site-footer"></div>`; `components/site-chrome/site-chrome.js` replaces them. Menu options, the contact email, the address, and the social links are all defined as constants at the top of that file — edit them there and every page changes at once. It also marks the current page's menu item with `.is-active` by comparing the filename from `location.pathname`. Unlike the data renderers, this file builds its markup with template strings rather than `createElement`, because the content is fixed and ours; there is no user-authored text in it.

**Accessibility invariants worth keeping.** `site-chrome.js` injects a "Skip to content" link as the first focusable element on every page; its target is `<main id="main-content">`, which every page must therefore have. The navbar CSS uses no `order` property on purpose — the ☰ toggle sits right after the logo in the markup so DOM order, visual order and tab order agree (reordering visually with `order` once made Tab skip the open menu entirely). Escape closes the mobile menu and returns focus to the toggle; class, `aria-expanded` and the ☰/✕ icon are synced by one function (`setMenuOpen`). Focus is deliberately *not* trapped in the open menu: it is a disclosure panel, not a modal. The skip link hides by `transform`, not `display:none`, which would make it unfocusable.

**Script order matters and is not enforced anywhere.** `site-chrome.js` must be loaded *before* `navbar.js` and `footer.js`, which query for `.navbar-toggle` and `#footer-year` — elements that do not exist until the chrome is injected. Likewise a page's data file must come before `cards.js` / `project-detail.js`, which read the globals (`projects`, `openCalls`, `workshops`). Each page loads only the data it needs; the renderers guard every global with `typeof … === "undefined"`, so a page that omits one simply renders nothing for it. `components/reveal/reveal.js` must be the *last* script on every page, because it observes the cards the renderers create.

**Scroll-reveal is progressive enhancement; the hidden state comes from JS, never CSS.** `reveal.js` adds `.reveal` (hidden) itself and the observer adds `.reveal-visible`, so with JavaScript disabled nothing is ever hidden. It exits immediately under `prefers-reduced-motion` or without `IntersectionObserver`. Both classes and the inline stagger delay are removed on `transitionend`, because `.reveal`'s `transition` would otherwise override the component's own (e.g. the `.card` hover) for as long as it stayed applied.

**`--color-accent` (violet) exists only for gradients next to `--color-primary`** — the hero title, `.btn-primary`, and the hero circles. It is never used on its own: everything else keeps the single-accent palette. `--shadow-glow` is the matching hover shadow on cards and the primary button; its rgba repeats `--color-primary`'s value because a shadow cannot reference another token without `color-mix`. The hero-title gradient sits inside `@supports (background-clip:text)` since without it the text would render transparent over a gradient box. On the landing page, `.section-alt` (tinted band via `color-mix`, with a plain `--color-surface` fallback) and `.section-eyebrow` (in `layout.css`) alternate section backgrounds so consecutive sections read as distinct.

**`components/<name>/` folders are source-of-truth for CSS and JS, but their `.html` files are only reference sheets.** No build step copies them anywhere. For `navbar` and `footer` the `.html` is now purely documentation of the CSS classes — the real markup lives in `site-chrome.js`, and editing the reference file changes nothing on the site. Every folder under `components/` corresponds to a component that actually ships; the design-system inventory in `docs/ui-design-system.md` is the record of what is still unbuilt, not empty placeholder files.

**All list content is rendered from data files, not written into the pages.** `assets/js/data/` holds `projects.js`, `open-calls.js`, `workshops.js`, `stats.js`, and `partners.js`; each declares one global array and carries editing instructions in its header comment for non-developers. Those five files are the only ones to touch to publish content — the pages themselves contain just an empty grid `<div>`. This is deliberate: calls and workshops turn over every semester, so requiring an HTML edit for them would defeat the "edit data, not code" goal.

`components/cards/cards.js` renders all the card types. `renderCardsInto(containerId, list, createCard, emptyMessage)` looks up a container id and returns silently if that page doesn't have it, which is how one script serves every page: `#projects-grid`, `#featured-projects` (first 3, on `index.html`), `#calls-grid`, and `#workshops-grid`. The card builders share small helpers (`createTitle`, `createTags`, `createFooter`, `createDetail`, `createCategory`, …) rather than repeating DOM construction. `project.html` is separate — it reads `?id=` from the URL and renders one project into `#project-content` via `project-detail.js`. Adding a project to the data file creates its card *and* its detail page automatically; there is no HTML file per project, and each project's `id` is part of its public URL, so renaming one breaks links already shared.

**Statistics and Partners hide their whole section when empty, instead of showing an empty-state message.** They are decoration on the landing page, so `renderOrHideSection()` (in `cards.js`) and `renderPartners()` set `section.hidden` rather than rendering a notice, which would look out of place there. `components/partners/` is its own component because a logo strip is not a card; it repeats the four lines of hide-when-empty logic on purpose rather than calling into `cards.js`, to avoid an invisible dependency between two components. Partners fall back to the partner's name as text when no `logo` file is set — which is the current state, since no partner logos are in the repo.

**Project `category` values double as research lines.** They are the same four strings shown on `research.html` (`Robotics`, `Computer Vision`, `Biomechatronics`, `Embedded Systems`). Changing one means changing both, and neither has been confirmed by CEDIM yet.

**Renderers build DOM with `createElement` + `textContent`, never `innerHTML`.** Project data is meant to be user-authored, and this keeps it from being parsed as HTML. They also tolerate missing fields (`project.tags || []`) and a missing `projects` global, because a hand-edited data file is expected to break occasionally — a broken data file should degrade to an empty state, not take the page down.

**The project data is a `.js` file rather than `.json` deliberately.** `fetch()` of a local JSON is blocked by CORS under the `file://` protocol, which would leave the projects section empty whenever a page is opened directly in a browser instead of served — the usual way this repo gets checked. A plain `<script>` with a `const projects = [...]` avoids that entirely and is just as editable through github.com's web editor. For the same reason `image` fields store a bare filename (`"brazo-robotico.svg"`), with the renderer supplying the `assets/img/projects/` prefix.

**`404.html` is picked up automatically by GitHub Pages** for any missing path, and it uses the same injected chrome as every other page. Its asset paths are relative like everywhere else, which works because the site is flat — a mistyped `/typo.html` still resolves them. A fabricated deep path (`/a/b/c`) would render it unstyled; that is accepted, since absolute paths would hardcode the repo name and break under a custom domain.

**The navbar and footer use the *white* logo variant, deliberately.** `site-chrome.js` injects `assets/img/logos/cedim-logo-white.svg`, sized to 40px tall with `width:auto` so no aspect ratio is imposed. The standard `cedim-logo.svg` is brand navy (`#11415E`) and would be near-invisible on the dark `#0B1120` background; it is kept only for eventual use on light backgrounds. The text styling on `.navbar-logo`/`.footer-logo` is retained on purpose so the image's `alt="CEDIM"` still reads well if the file ever fails to load. `favicon.svg` and `apple-touch-icon.png` are linked from every `<head>`; the latter has square corners because iOS applies its own rounding. Brand colours (`#11415E`, `#54AFDE`) do not match `--color-primary` (`#38BDF8`) — see `assets/img/logos/README.md`.

**Social preview tags are static and hardcoded per page.** Every page carries `description`, `canonical`, `og:*` and `twitter:*` tags in its `<head>`. `og:url` and `og:image` must be absolute URLs — crawlers do not resolve relative paths — so the base `https://cedimunifim.github.io/cedim-web/` is repeated in all seven files; a domain change means editing all of them. `project.html` is the exception: its tags are generic and deliberately omit `og:url`/`canonical`, because social crawlers do not execute JavaScript and therefore never see what `project-detail.js` writes. Per-project previews would require one HTML file per project, which would break the data-driven design.

**The `og:image` must be a raster file.** Facebook, LinkedIn, and WhatsApp do not render SVG previews, so all pages point at `assets/img/social/og-image.png` (1200×630, from the brand package) rather than reusing the site's SVGs. `og:image:width`/`og:image:height` are declared to match the file exactly and **must be updated in every page if the image is replaced** — networks may drop an image whose declared size disagrees with the file. `og-cedim.jpg` beside it is an unused 4:3 photo, kept in case a photo is preferred later; it would need cropping to 1200×630 first. This repo has no image tooling, so cropping and conversion happen outside it.

**Forms are always external.** CEDIM runs applications and sign-ups through Google Forms or Microsoft Forms; the site is the publicity layer and never collects data itself. Open calls and workshops carry `actionLabel`/`actionHref` fields for that, and `createAction()` in `cards.js` adds `target="_blank"` plus `rel="noopener noreferrer"` whenever the URL is external. Do not build in-page form handling — there is no backend to receive it.

**Content editing = commit.** The chosen approach for project CRUD is "edit the data file on github.com, GitHub Pages redeploys in ~1 min". A CMS admin panel (Decap) was considered and deferred: it authenticates through GitHub OAuth, which needs a server-side secret exchange that GitHub Pages cannot perform, so it would require deploying a separate OAuth service. If a form-based admin UI becomes a real need, the cheapest path is moving *hosting* to Netlify or Cloudflare Pages (repo stays on GitHub) for their built-in identity — the data layer above does not have to be rebuilt for it.

**`components/buttons/` is a style-only component.** Unlike the section components above, it ships no markup into `index.html` — it defines the `.btn` class plus variant modifiers (`.btn-primary`, `.btn-secondary`, `.btn-ghost`, `.btn-outline`, `.btn-danger`, `.btn-icon`) and states (`:disabled`/`.btn-disabled`, `.btn-loading`) that other components consume. `components/buttons/buttons.html` is a reference sheet of every variant, not a snippet to copy in.

**Inter is self-hosted, not linked from Google Fonts.** `assets/css/fonts.css` declares the variable font (weights 400–700, one file) from `assets/fonts/`, with `font-display:swap` and two `unicode-range` subsets so the browser fetches only what a page needs — normally just the 48 KB latin file. Before this the site declared `Inter` in `--font-family` but never loaded it, so nearly every visitor saw `system-ui` instead. Redistributing the files requires keeping `assets/fonts/OFL.txt` (SIL OFL 1.1) alongside them. There is no `<link rel="preload">` for the font: it would mean editing all eight pages for a marginal first-paint gain.

**CSS loads through a single entry point with a fixed cascade order.** Every page links only `assets/css/styles.css`, which `@import`s in this order: `fonts.css` → `variables.css` → `layout.css` → `components.css` → `utilities.css`. `components.css` in turn `@import`s each component's own stylesheet by relative path (e.g. `../../components/navbar/navbar.css`) — those paths resolve against the CSS file's own location, which is why they work identically from every page. When adding a new component's CSS, register its `@import` in `assets/css/components.css`, otherwise it is never loaded.

**Import order in `components.css` is load-bearing.** Equal-specificity rules are resolved by source order, so a component imported later wins. This already bit once: `.navbar-cta` composes `.btn .btn-primary`, and because `buttons.css` is imported after `navbar.css`, the mobile rule hiding the CTA had to be written `.navbar .navbar-cta` to outrank `.btn`. Prefer raising specificity in the component that owns the behavior over reordering the imports.

**Shared page-level classes live in `layout.css`, not in a component.** `.page` (top padding that clears the 72px fixed navbar), `.page-title`, `.page-intro`, `.prose`, and `.section-actions` are used by every interior page. `html { scroll-padding-top: 72px }` is there for the same reason — without it, in-page anchors land under the navbar.

**Design tokens live in `assets/css/variables.css`** as CSS custom properties on `:root`: colors, the `--font-size-xs`…`--font-size-8xl` type scale, `--shadow-md`/`--shadow-lg`, spacing `--space-1`…`--space-8`, border radii, transition, container width, font family. Component and layout CSS must consume these rather than hardcoding values. Two deliberate exceptions: the navbar toggle's `1.8rem` (it sizes the ☰ glyph, not text) and literal `border-radius:50%` for circles.

**Only tokens with a consumer are declared.** `docs/ui-design-system.md` also names an Info status colour, spacing steps of 96/128, "Extra Large"/"Rounded" radii and a third shadow level; none are in `variables.css`, because a token file that accumulates unused values stops describing the system. Add them when something needs them. The type scale was extracted from the values components already used, so it introduced no visual change — which is also why `--font-size-md` (1.1rem) and `--font-size-lg` (1.15rem) sit under 1px apart.

**There is one breakpoint: 992px.** The five-tier scale in the design spec was considered and rejected as ceremony, because the card grids use `repeat(auto-fill, minmax(300px, 1fr))` and reflow continuously — tablets get two columns and desktops three or four with no media query. `--breakpoint-mobile` records the value but cannot be used in `@media` (media queries can't read custom properties), so each component repeats `992px` literally. Known trade-off: between 768 and 992px the hamburger appears despite there being room for the full menu.

**The docs in `docs/` are now reconciled with the code, but they remain vision documents.** `ui-design-system.md`, `landing-blueprint.md`, `product-design.md`, `software-architecture.md` and `components/navbar.md` were audited and their factual claims corrected; what stays is intentionally forward-looking (FastAPI backend, PostgreSQL, dashboard, inventory, AI). Treat unbuilt items there as a roadmap, not a description. One open contradiction, flagged for CEDIM to settle: `product-design.md` plans a self-hosted FastAPI + PostgreSQL + VPS stack, while the admin-panel note below argues the cheapest path is moving hosting to Netlify or Cloudflare Pages.

## Conventions (from `docs/ui-design-system.md`)

- CSS classes: kebab-case (BEM planned for the future, not yet in use)
- JavaScript: camelCase
- Theme: dark by default (light theme planned but not implemented); base colors `--color-bg: #0B1120`, `--color-surface: #111827`, `--color-primary: #38BDF8`
- Icons: Lucide, outlined style
- Breakpoint used in current CSS: single mobile/desktop split at `992px` (`@media (max-width: 992px)`)

## Branches

- `develop` — active development
